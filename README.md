Part 3: Partie A – Conception du service (A.2)1. Pourquoi les calculs directs utilisent-ils le verbe GET et non POST ?Un calcul direct est juste une lecture : il ne modifie rien sur le serveur. GET est fait pour ça (il est sûr et sans effets secondaires). POST, à l'inverse, sert à créer ou modifier des données sur le serveur.2. Dans /calcul/somme?a=2&b=3, comment s'appelle la partie située après le point d'interrogation ?C'est la chaîne de requête (query string). Les éléments a=2 et b=3 sont des paramètres de requête sous forme de paires clé-valeur.3. Quelle différence entre /operations et /operations/3 ?/operations représente toute la collection des opérations, tandis que /operations/3 cible une ressource précise dans cette collection (l'opération numéro 3).4. Quel code de statut HTTP pour /operations/99 si cette opération n'existe pas ?404 Not Found.Part 5: Partie C – Premier service REST : la sommeQuestion C.1. Remplacez GET par POST dans Postman. Quel code de statut obtenez-vous ? Expliquez-le.Statut : 405 Method Not Allowed.Explication : L'URI existe, mais la méthode Java n'écoute que le verbe GET (@GET). JAX-RS renvoie donc un 405 pour indiquer que la ressource est là, mais que le verbe HTTP utilisé n'est pas autorisé.Part 6: Partie D – Compléter la calculatriceQuestion D.1. Quelle valeur JAX-RS donne-t-il à un paramètre entier absent ?Comme le paramètre est un type primitif int, JAX-RS lui assigne la valeur par défaut de Java, soit 0. Par exemple, somme?a=2 calcule $2 + 0 = 2$.Question D.2. Quel statut obtient-on quand le paramètre n'est pas un entier ? La méthode somme a-t-elle été exécutée ?Statut : 404 Not Found (car la conversion du paramètre échoue avant d'atteindre la méthode).Exécution : Non, la méthode n'est pas exécutée du tout ; l'erreur est interceptée par Jersey pendant la lecture des paramètres.Question D.3. Différence entre @QueryParam et @PathParam ? Laquelle pour lire l'identifiant dans /operations/{id} ?@QueryParam lit les paramètres dans l'URL après le point d'interrogation (?param=valeur), parfaits pour les filtres ou options.@PathParam lit les variables directement intégrées dans le chemin de l'URL (définies par {nom} dans @Path).Pour /operations/{id}, on utilise @PathParam("id").Part 7: Partie E – Échanger des données en JSONQuestion E.1. Aucune ligne de code n'écrit ce JSON. Qui a effectué la conversion ? D'où viennent les noms a, b, operation, resultat ?Qui l'a fait : C'est Jersey (via JSON-B / Eclipse Yasson) qui convertit automatiquement l'objet Java en JSON grâce à l'annotation @Produces(MediaType.APPLICATION_JSON).D'où viennent les noms : Des accesseurs (les getters) de la classe Resultat (convention JavaBean : getResultat() devient resultat, getA() devient a, etc.).Question E.2. Pourquoi la seconde requête (Accept: application/xml) est-elle refusée ?Le client demande explicitement du XML, mais le service n'est configuré (via @Produces) que pour renvoyer du JSON. Le serveur refuse donc de répondre dans un format non supporté et renvoie un 406 Not Acceptable.Part 9: Questions de synthèse1. Quelle est la différence entre JAX-RS et Jersey ?JAX-RS (Jakarta RESTful Web Services) est simplement une spécification (un standard qui définit les annotations et interfaces).Jersey est une implémentation concrète de cette spécification (le moteur qui fait réellement fonctionner le tout derrière).2. Quel est le rôle de Tomcat ? Pourquoi utiliser un .war et non un .jar exécutable ?Tomcat est un serveur d'applications web (un conteneur de servlets) qui gère les requêtes HTTP et fait tourner notre application.On utilise un .war (Web Application Archive) parce que l'application est conçue pour vivre à l'intérieur de ce serveur existant, contrairement à un .jar exécutable qui embarquerait son propre serveur et tournerait de manière autonome.3. Qu'est-ce que le principe "Stateless" et comment s'applique-t-il ici (puisqu'on stocke les opérations) ?Stateless signifie que le serveur ne garde aucune mémoire de la conversation d'un client d'une requête à l'autre : chaque requête doit contenir toutes les informations nécessaires.Le fait de stocker des opérations en mémoire ne brigue pas cette règle : il s'agit de données d'application partagées (l'état de la ressource, comme le ferait une base de données), et non d'une session ou d'un état propre à un client particulier.4. Quelle est la différence entre répéter un POST /operations et répéter un PUT /operations/1 ?POST n'est pas idempotent : si on l'exécute deux fois, on crée deux ressources distinctes (deux opérations avec des ID différents).PUT est idempotent : si on l'exécute deux fois de suite avec les mêmes données, on écrase simplement l'opération existante à l'identique. L'état final du serveur reste rigoureusement le même.
